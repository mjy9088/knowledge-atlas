# Local content studio

Run `pnpm studio` and open `http://127.0.0.1:4180`. This is a private authoring/review tool, outside public reader asset roots and the public catalog. It has no publication action. `STUDIO_PORT`, `STUDIO_DATA_DIR`, `STUDIO_CONCURRENCY` (1–4, default 2) and `STUDIO_CODEX_BIN` configure the local server. The Codex executable must be installed and authenticated separately; no account token is sent to the browser. Use the ordinary CLI sandbox/approval controls, not a bypass flag.

## Working contract

The initial manuscripts are binary relations, Monty Hall with an abbreviated statement missing the host policy, and the two-child observation problem. They are real editable **draft manuscripts/storyboards**, not published articles or completed interactive lessons. Their source locators, bounded claims, goals, concept introductions, planned durations and visual descriptions are in [examples.ts](examples.ts). Source consultation is not frozen-byte verification, rights clearance or expert approval. The finite probability examples are independently derived under declared assumptions. No third-party prose/figures/code are copied. Promotion into the public catalog requires the ordinary topic ownership, evidence and review process.

Edit the overall brief or selected slide, save, request a whole-flow and per-slide review, inspect findings, then record/resolve feedback. Unsaved input is retained while polling and cannot be silently discarded by topic/slide navigation. Initial-draft restoration is explicit. Optimistic revisions reject stale saves. Export returns the current plan, job reports and feedback; it does not publish or overwrite canonical article content. The initial three manuscripts are the current authoring scope; adding/removing arbitrary topics and slides, screenshots/audio attachments, automatic fixes and accepted-edit merge candidates remain planned.

## Reusable review policies

[contracts.ts](contracts.ts) owns three reusable policies: narrative/claims/timing, mathematical definitions/models/representations, and observation/selection processes in conditional probability. There are no topic-specific review checklists. Manuscript goals, scientific assumptions and scene sequence are review input, not custom review policy. The observation policy is shared by both probability manuscripts. Their context includes the existing base-rates article as a reusable explanation format; it does not claim that these are the same probability experiment.

Every review is a separate noninteractive read-only Codex run with the full narrative, requested target, policy checks, source scope and human notes. Requests and structured results use [the official noninteractive interface](https://learn.chatgpt.com/docs/non-interactive-mode): JSON events and a final output schema. No `.agents/skills` invocation or subagent cooperation is trusted as an enforcement mechanism. The host enumerates all required targets, bounds concurrency, records job status and validates the result. The selected CLI/account configuration supplies the model; no model or account override is invented.

Reports distinguish blocking findings from recommendations and quote the affected text. Timing is only estimated/unverified without actual audio/visual observation. Storyboard descriptions are not evidence of rendered fit, narration pacing, source verification or learning effectiveness. The reviewer cannot mark user feedback resolved. Agent review readiness is separate from content/expert/rights approval and publication.

## State and lifecycle

The server stores validated plans, feedback and review jobs in ignored `artifacts/studio/state.json` using atomic replacement. Each job gets its input, schema, bounded event log and response under `runs/<id>/`. No runtime report is fabricated when Codex is missing, unauthenticated, fails, times out or returns invalid JSON. The browser displays failure and the readiness gate stays blocked. Cancel queued/running jobs explicitly; server restart marks pending work interrupted without replaying model calls. Review calls have a ten-minute limit.

Review revisions cover the complete plan, reusable policy set, review protocol version and related base-rates source. Plan edits invalidate whole-flow and slide reviews conservatively. A queued old revision is interrupted; an already-running immutable old snapshot may finish but remains historical. Bump the protocol version for changed review instructions/execution meaning. Readiness requires the latest current-revision review of every slide and overall flow, no blocking findings, no unresolved user feedback/questions and a total slide budget within the content budget. Warnings remain visible. A successful process exit alone is not review evidence.

The server binds only to loopback and rejects foreign Host/Origin writes, bounded JSON payloads, unknown actions, arbitrary file access and stale writes. The browser receives typed actions rather than a general shell endpoint. One server owns one data directory; do not run competing servers against it. Cancellation terminates the Codex process; external sandbox/tool process-tree behavior still depends on the host. It is not a remote multi-user service.

## Layout and verification

The private studio uses editable forms and bounded review/feedback lists. Its authoring page may scroll; this is distinct from a normal public reader scene's fitting contract. Narrow layouts stack the editor/review panes; navigation, save, feedback and cancel remain reachable. UI labels explicitly distinguish manuscript/storyboard preview from implemented visuals.

Run `pnpm typecheck`, `pnpm validate`, `pnpm test` and `pnpm test:studio`. The normal `pnpm test:ui` also runs studio browser checks after public static-reader regressions. Studio tests exercise the real local UI at desktop, narrow and 960×540 CSS/DPR 2. Controlled unit-test reviewers test queue/gate semantics; they are not actual editorial approvals. Browser failure tests use an intentionally unavailable executable and cannot complete review. Actual authenticated Codex calls require a separate smoke check. Public static build tests must continue to exclude studio assets/manuscripts/runtime state.

## Brief metadata and production

Each plan has independently editable format (`short` / `long`), depth (`light` / `deep`) and purpose (`interest` / `understanding` / `practice`), plus topics, prerequisites, included/excluded scope and intended outcome. Convenience presets do not force a duration or couple the axes permanently. Long plans support up to four hours and 160 slides; these are input bounds, not recommended pacing. Existing plans without metadata migrate from their saved title, goal and time budget; present but malformed metadata is rejected. Full metadata participates in review revisions and prompts. A light introduction still requires accurate bounded claims; a deep explanation need not fill its time budget.

The production pane creates one isolated Git worktree per content from the host checkout's committed HEAD, under ignored `artifacts/studio-workspaces/`, on a `codex/studio/` branch. Uncommitted host edits are not copied. Preparing a workspace projects the manuscript once into topic-owned article/claims/page sources, registers them only in that worktree, and reuses the shared reader. It creates a **prose-only draft**, not the storyboard's designed visuals. New source records retain pending revision/authorship/rights verification rather than inventing clearance. Existing workspace sources are never overwritten by plan saves or another preparation request. Plan changes require an explicit implementation request and rebuild.

Implementation requests run the real Codex CLI with `workspace-write` in that worktree, the saved brief, human feedback and explicit runtime paths. They can run independently for three contents, with only one writer/build per content. Git metadata remains outside the agent write sandbox; the host handles commits. No model override, package installation, sandbox bypass, merge, push or publication is added. A completed task means the process ended successfully; inspect its log and source diff, then build. It is not editorial approval or proof that every request was satisfied. Preparation failures preserve partial sources for inspection; automatic destructive retries are intentionally unavailable.

The build action runs strict type checking, repository validation and the actual static builder against worktree sources. Source fingerprints (HEAD, binary diff and untracked files) must match before/after the build. Successful output is copied into an immutable local build snapshot, tagged with the last completed preparation/implementation task’s plan revision, source fingerprint, creation time and build ID. Saving a new brief and rebuilding alone does not relabel old implementation sources as the new brief. This linkage records task context, not proof of semantic fulfillment. A failed build retains the previous successful snapshot. No host catalog or public build output is changed. A snapshot reflects saved sources, and must be rebuilt after manual/agent edits even if the plan revision is unchanged.

Snapshots are served from separate loopback origins and displayed in a sandboxed iframe, with an external-window link. The Studio scene selection sets the preview's initial hash; navigation inside the actual reader remains independent. The build-feedback button records the snapshot ID, source fingerprint and Studio-selected slide in the editable feedback text; verify that selection if you navigated inside the iframe. The preview origin has no Studio write API; Studio rejects its cross-origin writes. Static paths are contained, linked build files are rejected, and preview servers expose GET/HEAD only. Snapshots and logs remain ignored local artifacts. Restart interrupts production jobs without replay and restores existing preview snapshots on newly allocated ports. Worktrees/snapshots are retained for manual review; automatic archival and storage quotas remain future work.

## Conversations, questions and approvals

The production pane's conversation UI uses the installed CLI's [official App Server interface](https://learn.chatgpt.com/docs/app-server) over private stdio JSON-RPC. No separate API key, browser token handling, model override or WebSocket listener is introduced. Sending a message explicitly supplies that message, the saved content brief, revision and feedback to the authenticated Codex runtime. Read-only questions use a read-only sandbox; implementation requests use the content's isolated worktree and require workspace preparation. Both hold the same per-content lease as builds/writers. They cannot run concurrently against one content, and the shared production limit is three active contents.

Each conversation records the precise Codex thread ID. A later message resumes that ID, never an ambient `--last` thread. New conversations preserve old history, selectable from the UI. If workspace preparation changes the working directory, the next message starts a new runtime thread with bounded visible conversation context rather than resuming another directory. Saved briefs are supplied each turn; text replies do not silently change the plan, resolve feedback, approve publication or satisfy independent editorial review. Legacy one-shot implementation runs remain visible in execution logs; they are not fabricated chat history.

Public assistant text, tool summaries, user messages and errors are persisted in ignored `chats.json`. Streamed updates are coalesced; semantic boundaries flush the latest snapshot. Atomic replacement retries transient file-sharing locks without falling back to a partial direct overwrite. Reasoning internals, auth tokens and raw RPC traffic are not stored as chat messages. Individual displayed messages and tool output are bounded. The browser polls for incremental updates while retaining composer drafts across content navigation. Question forms retain non-secret partial answers across polling/navigation; secret answers are not copied to persisted answer summaries or draft caches. Unsent input is not restored after a full browser reload.

Blocking/nonblocking `item/tool/requestUserInput` requests render actual questions with options and free text, and send the exact answer map back to the originating live request. Plain-text or asynchronous assistant questions can be answered in the composer, including through `turn/steer` with an expected active-turn ID. Command/file approval requests show reason, command/directory or the emitted file proposal. Only an explicit click can approve once; there is no session-wide approval or policy-amendment action. Read-only conversations cannot approve escalation. Requests outside this supported subset receive an unsupported error without permission grants; MCP forms, auth flows and network/filesystem permission-grant editors remain unsupported. Configured CLI/managed approval policies can resolve or reject work without emitting a human approval request; the Studio does not override that reviewer or manufacture a prompt.

Request replies are scoped to content, conversation and live turn, and disappear after resolution, completion, interruption or restart. No answer, approval or model call is replayed on server restart. Stop requests `turn/interrupt`, then closes the transport; server disposal closes active connections and records interruption. Local process-tree cleanup remains subject to the CLI/host sandbox. Each turn has a thirty-minute bound. Failed/missing CLI execution stays failed and cannot produce assistant/review evidence. Production builds remain explicit and separate from conversation success.

Validate transport/question/approval lifecycle with controlled protocol fixtures and browser UI fixtures; these are not actual model answers or execution approvals. A real authenticated content-bearing chat smoke requires authorization to send that draft/context. A successful local protocol handshake alone does not verify inference, account access or model-emitted questions.
